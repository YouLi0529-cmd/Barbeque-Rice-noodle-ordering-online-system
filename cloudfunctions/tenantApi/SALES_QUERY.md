# 销量查询：更新与核对

## 更新范围

- 后端：`index.js` 接入 `salesQueryService.js`，四个固定团购标识在 `salesQueryPackages.json`。
- 小程序：营业统计页的 JS/WXML/WXSS，以及 `miniprogram/utils/salesQuery.js`。
- 不新增数据集合、不执行数据库写入、不改实际结账金额。
- 本功能尚未自动部署、上传 GitHub 或发布。

## 上线步骤

1. 先将完整 `cloudfunctions/tenantApi` 上传部署（云端安装依赖），包括两个新服务文件。
2. 在微信开发者工具重新编译，营业统计 → 销量查询，验证普通品类和团购。
3. 体验版对账通过后，再上传、审核、发布小程序，手机正式版才会显示入口。
4. 无需重新安装或注册 Print Agent。

不要只部署 `tentApi`，也不要只上传 `index.js`。

## 口径

- 当前门店、堂食、已完成结算且仍有效的订单；已支付清台历史仍保留。
- 按北京时间的结账日，开始日 00:00:00（包含）至结束日次日 00:00:00（不含）。
- 只读有效订单目前的 `goods`，因此结算记录删除菜品、订单、整条记录后会同步排除。
- 仅部分付款、订单尚未标记已结账的记录不纳入。`checkoutPayment` 和付款事件只做财务记录，不重复累加菜品。
- 优先使用 `originalPrice`（下单时读取的菜单价）。普通非赠送、非套餐菜品可使用订单本身保存的 `price`；不能读取现价补历史数据。
- 普通品类按历史 `categoryId`；只有分类名称没有标识的旧记录单独列为历史分类，不猜测它对应哪个当前分类。
- 四个固定团购：4-5人小聚套餐、双人餐、小熊柠檬茶、桂花酸梅汤。名称动态读取，套餐删除后保留已核实名称及“已删除”标记。
- 一个订单同一套餐按保存的 `packageCount` 只加一次；只要有一项套餐菜品剩余，就统计原套数，全部移除计0。
- 其他新建0元套餐不自动加入四个固定团购，但其中菜品仍可进入普通品类销量。
- 元金额以整数分累加并格式化，赠送和套餐分摊0元不会替代菜单原价。

## 分页、并发与失败

正常订单明细查询在数据库端限定 `checkoutAt` 的北京时间日期范围和查询截止点。对这个条件的严格补集（`nor`），只分页读取结账时间、状态等轻量字段，再按原有时间字段优先级判断；只有实际属于所选日期的旧格式订单才补读菜品明细。两组互斥并覆盖全部候选，不假设历史结账时间一定是Date，也不忽略缺少时间的记录。完整读取所需字段使用投影，省去厨房日志、打印记录等无关内容。

明细分页100条，历史轻量字段分页请求1000条；品类历史扫描、订单汇总和核对每次云端请求连续处理最多20页，处理约3秒后在页边界返回游标（单次数据库读取仍可能超出此时间）。没有总记录数截断。订单读取以空页为结束，即使服务端把请求的1000条压到100条也不会截断。使用 `_id` 游标和每组首批读取的上界，不用容易因删除而跳项的 offset 分页。仍需审查范围外的历史时间字段，但不再下载全部历史菜品明细；实际耗时取决于订单量、索引和云端响应。

响应包含 `queryPlan: date-range-v2`、`headerReads`、`detailReads`、`elapsedMs`，便于在开发者工具Network中确认部署版本和读取量。两次扫描都计入读取量；新版本拒绝旧查询游标，需要重新点击查询。没有使用缓存或写入汇总表。

查询开始时固定时间截止点，不计入之后才结账的订单。初次汇总后再分页校验记录指纹；检测到期间发生删除、退菜或明细变更时，报“查询期间结算记录有变化，请重新查询”，不展示部分统计。这是两遍读校验，不是数据库跨请求事务快照，不能承诺在持续修改数据期间获得绝对原子快照；要对账时请避免同时编辑所查结算记录。

界面只有在所有页及校验全部完成后才显示合计。取消会忽略未完成请求的返回。查询状态绑定门店、管理员、日期、品类，最长有效一小时，超时需重查。

缺少明确结账时间、目标菜品的历史价格、分类、有效套餐套数等时，返回明确的历史数据不足错误，并给出订单标识，不默认为0。缺少结账时间的已支付历史订单会阻止查询，因为无法确定它是否属于所选日期。分类选项扫描也会在历史分类不足时明确失败，不伪装成完整列表。

查询由 `admin.business.*` 鉴权保护。数据库查询使用 CloudBase 查询指令和字段投影。若线上提示索引不足，查看云函数日志中的 `sales query failed` 原始错误，按云端建议建立索引再重试；不要改成只读前100/1000条。涉及 `order` 的门店、类型、支付状态、删除标志、`checkoutAt` 日期范围及 `_id` 范围排序，`dish` 的分类及 `_id` 排序，`dishCategory` 的菜单类型及 `_id` 排序。具体索引是否需要补充必须以线上查询计划为准。

## 人工对账样例

1. 选择结算记录中一个完整营业日，只核对有效堂食记录，不含已删除记录。
2. 检查一个品类的每条订单剩余菜品：份数求和，菜单原价逐条乘份数后求和。
3. 改价样例：赠送菜2份、下单原价20元；套餐菜3份、下单原价25元，结果应为5份、115.00元，即使实收均为0。
4. 同一订单某团购2套、多个组成菜品都写 `packageCount: 2`：结果应为2套，不是组成菜品数乘2。
5. 删除其中一道套餐菜后仍为2套；最后一道也移除后为0套。可先用测试环境验证，勿为测试删除真实营业记录。
6. 删去结算记录中的订单或整条记录后重新查询，确认对应贡献消失。
